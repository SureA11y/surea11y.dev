Before you start

These procedures describe what to check and how to decide. A few habits make the results reliable, whichever browser and assistive technology you use.

  • Test with at least two pairs of browser and screen reader that your users have. Common pairs are NVDA with Firefox or Chrome and JAWS with Chrome on Windows, VoiceOver with Safari on macOS and iOS, and TalkBack with Chrome on Android. Screen readers and browsers differ in what they announce, so a result in one pair is not a result for all of them. When they disagree, record which pair failed.
  • Do keyboard tests with the screen reader turned off. In browse mode a screen reader can activate elements that the keyboard alone can't reach, which hides keyboard failures.
  • On a Mac, turn on Keyboard navigation in System Settings, under Keyboard, and in Safari turn on "Press Tab to highlight each item on a webpage" in the Advanced settings. Without them, Tab skips links and some controls, and you will record failures that are not there.
  • To start a keyboard pass at the top of the page, reload it and press Tab without clicking, or click an empty area just above the first link or control. Starting from the address bar is unreliable: some browsers first move focus through their own toolbar or the address bar's suggestions.
  • Each browser shows the accessibility tree in a different place: Chrome and Edge in the Accessibility pane of the Elements panel (turn on the full-page accessibility tree to see the whole page), Firefox in the Accessibility Inspector, and Safari in the Accessibility section of the Elements tab's Node panel. Where a procedure says "the developer tools' Accessibility pane", use the one of the browser you are testing.
  • The device toolbar of the developer tools changes the size of the viewport, but it doesn't reproduce a real phone's zoom, rotation, gestures or screen reader. Confirm mobile results on a real device.
  • Test each state the page can be in, not only how it first loads: open menus and dialogs, error messages, empty and full lists, signed-in and signed-out views.
  • Rules marked "evidence only" can't decide on their own. Treat what they report as a list of places to check by hand.

1 Perceivable

1.1 Text Alternatives

Non-text content that conveys something has a text alternative

For: 1.1.1

  • Rules decide part of it
  • Tools: The browser's developer tools
  1. Look through the whole page for content that isn't text: photos, icons, logos, charts, maps, diagrams, video posters, and the pictures inside buttons and links.
  2. For each, select it in the developer tools' Elements pane and read the Name in its Accessibility pane.
  3. Note each one that has no name and isn't hidden from assistive technology (with alt="", aria-hidden="true", role="presentation" or as a CSS background).
  4. Look also for information that only CSS shows: background images, icon fonts and pictures added with the content property. Inspect each, since there is no alt attribute to read, and check that what it shows is also given in text that a screen reader reads.
  5. For content that can't be described in a few words, such as a chart or a map, check that the name at least says what it is, and that a fuller description is on the page or linked beside it.
Passes when
Every piece of non-text content a person needs has a text alternative, or is hidden from assistive technology because it is decorative.
Fails when
Non-text content that conveys something has no text alternative, so a screen reader user meets an unnamed image or nothing at all, which fails WCAG 1.1.1.
Rules and facets

Rules that test it: img-alt-present, role-img-text-alternative-present, canvas-text-alternative-present, embed-text-alternative-present, svg-text-alternative-present, svg-image-text-alternative-present, object-text-alternative-present, video-poster-text-alternative-present, meter-name-present, progressbar-name-present

It also assesses: img-alt-attr-present, role-img-text-alternative-present, canvas-text-alternative-present, embed-text-alternative-present, svg-text-alt-present, svg-text-alternative-present, svg-image-text-alt-present, object-text-alternative-present, video-poster-text-alt-present, meter-name-present, progressbar-name-present

Result: Non-text content that conveys something has a text alternative

Images and icons used as controls are named by what they do

For: 1.1.1

  • Rules decide part of it
  • Tools: The browser's developer tools
  1. Find every link, button and other control whose only content is an image or icon, such as a logo that links home, a magnifier for search or a cross that closes a dialog.
  2. For each, select it in the developer tools' Elements pane and read the Name in its Accessibility pane.
  3. Check that the name says what the control does or where it leads ("Search", "Close", "Home"), not what the picture shows ("magnifying glass") or a file name.
Passes when
Every control made of an image or icon has a name that says what it does or where it goes.
Fails when
A control made of an image or icon has no name, or one that describes the picture rather than what it does, which fails WCAG 1.1.1.
Rules and facets

Rules that test it: input-image-alt-present, area-alt-present

It also assesses: input-image-alt-attr-present, area-alt-attr-present

Result: Images and icons used as controls are named by what they do

Decorative images are hidden from assistive technology, and only those

For: 1.1.1

  • Only a person can check it
  • Tools: The browser's developer tools
  1. Look through the page for images, icons and graphics that only decorate: borders, dividers, background pictures, ornaments, and pictures whose content the text next to them already gives.
  2. For each, select it in the developer tools' Elements pane and check in its Accessibility pane that it is ignored (alt="", aria-hidden="true", role="presentation", or a CSS background).
  3. For a decorative SVG drawn in the page, check that it has aria-hidden="true". Without it, some browser and screen reader pairs announce it as an image with no name, or read the text inside it.
  4. Then do the reverse: for each image that is hidden that way, ask whether a user would miss anything if it were gone: information, a label, a chart's data.
Passes when
Decorative images are hidden from assistive technology, and every image that is hidden is truly decorative.
Fails when
A decorative image is announced (often by its file name), or an image that conveys information is hidden from assistive technology, which fails WCAG 1.1.1.
Result: Decorative images are hidden from assistive technology, and only those

Each text alternative gives what its image gives

For: 1.1.1

  • Rules decide part of it
  • Tools: The browser's developer tools
  1. For each image and other non-text content that has a text alternative, read the alternative (the Name in the developer tools' Accessibility pane) and look at the content in its place on the page.
  2. Ask what the content gives a reader there, and check that the alternative gives the same: the words in an image of text, the point a photo makes, the facts a chart shows.
  3. Where the alternative only names a complex image, such as a chart or diagram, check that the details are in a caption, text or table next to it, or a link beside it, that a screen reader user can find from the image.
  4. Note alternatives that are a file name, a web address, a word such as "image" or "photo", or that repeat the text right next to them.
  5. Check the language of each alternative: it should be in the language of the page, or marked with its own.
Passes when
Each text alternative gives what its content gives in that place, directly or through a description a screen reader user can reach from it.
Fails when
A text alternative doesn't give what the content does, for example a file name, a generic word or a chart named without its data anywhere, which fails WCAG 1.1.1 (F30).
Rules and facets

Rules that test it: area-alt-quality, canvas-text-alternative-quality, embed-text-alternative-quality, img-alt-decorative, img-alt-quality, input-image-alt-decorative, input-image-alt-quality, object-text-alternative-quality, svg-text-alternative-quality

It also assesses: text-alt-quality-review, alt-suspicious-patterns

Result: Each text alternative gives what its image gives

A CAPTCHA says what it is for and offers another form that uses a different sense

For: 1.1.1

  • Only a person can check it
  • Tools: A screen reader
  1. Find any test the page uses to tell people from programs, such as distorted letters to type, pictures to pick or a puzzle to drag.
  2. Check that it has a text alternative that says what it is and what to do, without giving the answer away.
  3. Check that it offers another form that uses a different sense, such as an audio version of a visual test, or another way altogether, such as a code by email.
  4. Try the other form with a screen reader and the keyboard.
Passes when
The page has no such test, or the test says what it is and offers a form that uses another sense and can be completed.
Fails when
The test can only be passed by seeing (or only by hearing), or has no text saying what it is, which fails WCAG 1.1.1.
Result: A CAPTCHA says what it is for and offers another form that uses a different sense

1.2 Time-based Media

Prerecorded audio-only and video-only media has a transcript or an equivalent alternative

For: 1.2.1

  • Rules decide part of it
  • Tools: a browser only
  1. Find every audio player and every video without sound on the page, including ones in frames, and play each.
  2. For audio, look next to the player and elsewhere on the page for a transcript or a link to one.
  3. For a video without sound, look for a transcript, or an audio version that describes everything shown, that you can find and play from the page with the keyboard.
  4. Compare each alternative with the media and check that it gives the same information: speech, important sounds and what is shown.
  5. Leave out media that is itself an alternative for text on the page and is labelled as such.
Passes when
Every prerecorded audio-only or video-only item has a transcript, or for video an audio version, that gives what it gives, or is a labelled alternative for text on the page.
Fails when
Prerecorded audio-only media has no transcript, or prerecorded video-only media has neither a transcript nor an audio version with the same information, which fails WCAG 1.2.1.
Rules and facets

Rules that test it: media-alternative-transcript-evidence

Result: Prerecorded audio-only and video-only media has a transcript or an equivalent alternative

Prerecorded video with sound has captions

For: 1.2.2

  • Only a person can check it
  • Tools: a browser only
  1. Find every prerecorded video with sound on the page, including ones in frames and players of other sites.
  2. Play each with the sound on and note whether its sound carries information: speech, or sounds that matter.
  3. Where it does, look for captions: the player's CC button, captions burned into the picture, or a captioned version of the same video linked next to it. A transcript on its own doesn't replace captions.
  4. Leave out a video that is itself an alternative for text on the page and is labelled as such.
Passes when
Every prerecorded video whose sound carries information has captions, here or in a captioned version linked next to it, or is a labelled alternative for text on the page.
Fails when
A prerecorded video has dialogue or important sounds and no captions, here or in a linked captioned version, even if a transcript is offered, which fails WCAG 1.2.2.
Rules and facets

Rules that test it: video-caption

Result: Prerecorded video with sound has captions

Captions give all the dialogue, who is speaking, and the sounds that matter, in time with the video

For: 1.2.2

  • Only a person can check it
  • Tools: a browser only
  1. Play each captioned video with the sound on and the captions turned on.
  2. Compare the captions with what is said and heard, all the way through.
  3. Check that they carry all the dialogue, say who is speaking when that isn't clear, and describe the sounds that matter (music, alarms, laughter), and that they stay in time with the picture.
  4. Treat automatically generated captions with care: they often get names, numbers and punctuation wrong and don't describe sounds, so they rarely meet this criterion without editing.
Passes when
The captions carry all dialogue, the speakers where needed, and the important sounds, in time with the video.
Fails when
Captions leave out dialogue or important sounds, don't say who is speaking where that matters, or run out of time with the video, which fails WCAG 1.2.2 (F8).
Result: Captions give all the dialogue, who is speaking, and the sounds that matter, in time with the video

1.3 Adaptable

Text that looks like a heading is marked up as one, at a level that matches the page's outline

For: 1.3.1

  • Rules decide part of it
  • Tools: The browser's developer tools, A screen reader
  1. Look through the page and note every piece of text that works as a heading: it is larger or bolder than the text around it and introduces what follows.
  2. For each, check in the developer tools' Elements pane that it is an <h1> to <h6>, or has role="heading" with an aria-level.
  3. Check the reverse: each heading element on the page introduces content, rather than being used only to make text big.
  4. List the headings with a screen reader's headings list, a browser extension such as HeadingsMap, or the Accessibility pane, and check that their levels match the structure the page shows: a section's sub-headings sit below its heading, not at the same level or above it. A skipped level on its own, such as an h2 followed by an h4, doesn't fail this criterion when the nesting is still right. Record it as a best practice issue.
Passes when
Every visual heading is marked up as a heading, every heading element is one, and the levels follow the outline the page shows.
Fails when
Text that looks like a heading is plain text, a heading element is used only for its size, or the levels contradict the outline, so screen reader users can't find or follow the sections, which fails WCAG 1.3.1.
Rules and facets

Rules that test it: p-as-heading

It also assesses: p-as-heading-evidence

Result: Text that looks like a heading is marked up as one, at a level that matches the page's outline

Content shown as a list is marked up as a list

For: 1.3.1

  • Rules decide part of it
  • Tools: The browser's developer tools
  1. Look through the page for content shown as a list: items in a row or column with bullets, numbers or the same layout, such as menus, steps and groups of links.
  2. For each, check in the developer tools' Elements pane that it is a <ul>, <ol> or <dl> (or has role="list" with role="listitem" items).
  3. Check that each list holds only list items directly, and each list item sits in a list.
  4. If you test with VoiceOver and Safari, know that Safari does not expose a list whose bullets are removed with list-style: none unless it has role="list". This is a choice of the browser, not a failure of the page, but note it when the list's structure matters to the user.
Passes when
Content shown as a list is marked up as a list, and list markup is complete.
Fails when
Content shown as a list is a run of paragraphs, line breaks or divs, or list markup is broken, so a screen reader doesn't say it is a list or how many items it has, which fails WCAG 1.3.1.
Rules and facets

Rules that test it: list-children-valid, listitem-parent-valid, definition-list-children-valid, dlitem-parent-valid

It also assesses: list-children-valid, listitem-parent-valid, definition-list-children-valid, dlitem-parent-valid

Result: Content shown as a list is marked up as a list

Data tables mark up their headers and caption, and tables used only for layout carry no header markup

For: 1.3.1

  • Rules decide part of it
  • Tools: The browser's developer tools, A screen reader
  1. Find every table on the page, and every grid of data drawn without a table.
  2. For a table of data, check in the developer tools' Elements pane that its header cells are <th> (with scope where a header is not plainly a row or column header) and that a title shown above it is its <caption>.
  3. For a complex table, with headers on more than one level, check that each data cell names its headers with a headers attribute or scope.
  4. With a screen reader, move through a few data cells and check that it reads their headers with them.
  5. For a table used only to lay things out, check that it has no <th>, <caption> or summary.
Passes when
Data is in tables whose headers and caption are marked up, a screen reader reads each cell's headers, and layout tables carry no header markup.
Fails when
A table of data has no header markup or a fake caption in a cell, data is laid out as a grid without a table, or a layout table is marked up as data, which fails WCAG 1.3.1.
Rules and facets

Rules that test it: table-headers-attr-valid, table-th-has-data-cells, table-fake-caption, td-has-header

It also assesses: table-headers-attr-valid, table-th-has-data-cells, table-fake-caption-evidence, td-has-header

Result: Data tables mark up their headers and caption, and tables used only for layout carry no header markup

Form fields are tied to their visible labels, and groups of fields to the text that names the group

For: 1.3.1

  • Rules decide part of it
  • Tools: The browser's developer tools, A screen reader
  1. Find every form field on the page: text fields, check boxes, radio buttons, drop-downs and custom controls.
  2. For each, select it in the developer tools' Elements pane and check that the Name in its Accessibility pane contains its visible label.
  3. For a group of fields under one question, such as radio buttons or a date in three parts, check that the group is a <fieldset> with a <legend>, or has role="group" with a name, so the question is read with each field.
  4. Check that instructions shown next to a field (a format, a required mark) are tied to it with aria-describedby or are in its label.
Passes when
Every field's name includes its visible label, groups of fields are named by their question, and a field's instructions are tied to it.
Fails when
A field is labelled only by nearby text that isn't tied to it, or a group's question isn't tied to its fields, so a screen reader reads a field without saying what it is for, which fails WCAG 1.3.1.
Rules and facets

Rules that test it: form-control-programmatic-label-present

It also assesses: form-control-programmatic-label-present, form-control-label-quality-review

Result: Form fields are tied to their visible labels, and groups of fields to the text that names the group

ARIA roles and relationships give the same structure the page shows

For: 1.3.1

  • Rules decide part of it
  • Tools: The browser's developer tools
  1. Find the parts of the page built with ARIA roles: custom menus, tabs, trees, grids, lists and listboxes.
  2. For each, open the developer tools' Accessibility tree and check that the structure it shows matches what is on screen: a tablist holding tabs, a menu holding menu items, a grid holding rows and cells.
  3. Check that no element with a role is missing the parent or children its role needs, and that aria-owns, where used, gives each element a single owner.
  4. Check that <body> is not hidden with aria-hidden="true".
Passes when
The accessibility tree gives the structure the page shows, with every role in the place its role needs.
Fails when
A role is missing its required parent or children, owned twice, or the page is hidden from the tree, so assistive technology gives a structure that doesn't match the screen, which fails WCAG 1.3.1.
Rules and facets

Rules that test it: aria-hidden-body, aria-required-children, aria-prohibited-children, aria-required-parent, aria-roles-valid, aria-owns-valid

It also assesses: aria-hidden-body-absent, aria-role-required-owned-children, aria-role-owned-children-allowed, aria-role-required-context-parent, aria-role-valid, aria-owns-valid

Result: ARIA roles and relationships give the same structure the page shows

Meaning shown by styling or layout, such as bold, colour, position or an asterisk, is also given in the markup or the text

For: 1.3.1

  • Only a person can check it
  • Tools: The browser's developer tools, A screen reader
  1. Look for meaning that the page shows only by how things look: required fields marked by an asterisk or colour, emphasised or struck-through words, a selected item shown by its style, text set apart in a box.
  2. For each, check whether the same meaning is in the markup (such as required, aria-current, <em>, <del>) or in the text itself ("required", "current page").
  3. Look at text and icons added with CSS, through the content property. Browsers differ in whether screen readers read them, so information that only CSS adds must also be in the markup or the text.
  4. Read the parts with a screen reader and check that what the styling shows is said.
Passes when
Whatever the styling or layout conveys is also in the markup or the text.
Fails when
Meaning is given only by styling or position, such as required fields marked only by colour or an unexplained asterisk, so a screen reader user misses it, which fails WCAG 1.3.1.
Result: Meaning shown by styling or layout, such as bold, colour, position or an asterisk, is also given in the markup or the text

The page works in both portrait and landscape, unless one orientation is essential

For: 1.3.4

  • Rules decide part of it
  • Tools: The browser's developer tools
  1. Open the page in the developer tools' device toolbar, or on a phone or tablet.

Fails when
The page works in only one orientation, by asking to rotate the device, turning its content or hiding it, with no essential reason, which fails WCAG 1.3.4.

Fields that ask for information about the user name its purpose with the right autocomplete value

For: 1.3.5

  • Rules decide part of it
  • Tools: The browser's developer tools
  1. Find every field that asks for information about the person using the page: name, email, phone, address, birthday, username, password, card details.
  2. For each, read its autocomplete attribute in the developer tools' Elements pane.
  3. Check that it is the value that matches what the field asks for (name, email, tel, street-address, postal-code, bday, username, new-password, cc-number and so on).
  4. A field with autocomplete="off", or with no autocomplete attribute, doesn't identify its purpose, even when the browser still offers to fill it in.
  5. Leave out fields that ask about someone else, such as a gift recipient, unless they say so with the right section or value.
  6. Only the purposes in WCAG's list of input purposes are in scope. A field for a membership or customer number, for example, has no value in that list and needs none.
Passes when
Every field that asks for the user's own information has the autocomplete value that matches it.
Fails when
A field that asks for the user's own information has no autocomplete value, or a wrong one, so the browser and assistive tools can't fill it in or mark its purpose, which fails WCAG 1.3.5.
Rules and facets

Rules that test it: autocomplete-valid

It also assesses: autocomplete-valid

Result: Fields that ask for information about the user name its purpose with the right autocomplete value

1.4 Distinguishable

Colour is not the only way information is shown, a choice is asked for or an element is set apart

For: 1.4.1

  • Rules decide part of it
  • Tools: The browser's developer tools
  1. Look for information the page gives by color: links in a paragraph, required or invalid fields, the selected tab or day, chart series, status in red or green.
  2. For each, check whether something besides colour gives it too: an underline, an icon, a text label, a pattern, a border or a change of shape.
  3. For links in a paragraph that differ only by colour, check that they get an underline or other mark when hovered and focused, and that their colour has a contrast of at least 3:1 with the text around them.
  4. View the page in greyscale (in the developer tools' Rendering pane, emulate achromatopsia) and check that nothing is lost.
Passes when
Everything the page gives by colour is also given another way.
Fails when
Information, such as which fields have errors or which text is a link, is given only by colour, which fails WCAG 1.4.1.
Rules and facets

Rules that test it: link-in-text-block

It also assesses: link-in-text-block

Result: Colour is not the only way information is shown, a choice is asked for or an element is set apart

Sound that plays by itself for more than 3 seconds can be paused, stopped or turned down

For: 1.4.2

  • Only a person can check it
  • Tools: A keyboard
  1. Load the page with the sound on and listen for sound that starts by itself: music, a video, an advertisement.
  2. Where sound plays for more than 3 seconds, look near the top of the page or the player for a way to pause or stop it, or to turn its volume down apart from the computer's volume.
  3. Check that the control can be found and used with the keyboard.
Passes when
No sound plays by itself for more than 3 seconds, or a control near the start of the page pauses, stops or lowers it.
Fails when
Sound plays by itself for more than 3 seconds with no way to pause, stop or lower it apart from the computer's volume, so it drowns out a screen reader, which fails WCAG 1.4.2.
Rules and facets

Rules that test it: no-autoplay-audio

Result: Sound that plays by itself for more than 3 seconds can be paused, stopped or turned down

Text has a contrast of at least 4.5:1 with its background, or 3:1 when large

For: 1.4.3

  • Rules decide part of it
  • Tools: The browser's developer tools
  1. Look through the page for text that seems faint against its background: light grey text, text on coloured panels, placeholders, text over images or gradients, text in buttons.
  2. For each, inspect it and click the swatch of its colour in the developer tools' Styles pane: the picker shows its contrast ratio with the background.
  3. The colour picker measures against the background colour set in CSS. Where text sits on an image, a gradient or a semi-transparent layer, or its colour comes from opacity or a blend mode, the picker's figure is not reliable: use the next step instead.
  4. Where the background is an image, a gradient or a semi-transparent layer, measure the text against the part of the background where it is least visible, with a colour contrast checker.
  5. Check the ratio is at least 4.5:1, or 3:1 for large text: at least 24 pixels (18pt), or 18.66 pixels (14pt) and bold.
  6. Don't round the result: 4.49:1 fails. Check text in its other states too, such as on hover, on focus and when selected, since a state can lower the contrast.
  7. Leave out logos and brand names, text on controls that are disabled, text that is only decoration or that nobody can see, and text that is part of a picture with other important content, such as a street sign in a photo.
Passes when
All text and images of text have a contrast of at least 4.5:1 with their background, or 3:1 when large.
Fails when
Text has less contrast with its background than 4.5:1 (3:1 for large text), so people with low vision can't read it, which fails WCAG 1.4.3.
Rules and facets

Rules that test it: contrast-minimum, contrast-computable

It also assesses: contrast-computability-143

Result: Text has a contrast of at least 4.5:1 with its background, or 3:1 when large

Text can be resized to 200% without losing content or function

For: 1.4.4

  • Rules decide part of it
  • Tools: The browser's zoom
  1. Zoom the browser to 200%.
  2. Go through the whole page and check that all text has grown, and none is cut off, overlapped or hidden.
  3. Use the page's controls, menus and forms at that size and check that they all still work.
  4. On a phone, check that you can pinch to zoom the page to 200%. Use Chrome on Android with its "Force enable zoom" accessibility setting turned off: Safari on iOS ignores a viewport that blocks zoom, so it can hide this failure.
  5. Leave out captions and images of text.
Passes when
At 200% all text has grown and stays readable, and everything still works.
Fails when
At 200% text is cut off, overlaps or doesn't grow, a control stops working, or pinch zoom is blocked, which fails WCAG 1.4.4.
Rules and facets

Rules that test it: meta-viewport-zoom-enabled

It also assesses: meta-viewport-zoom-enabled

Result: Text can be resized to 200% without losing content or function

Text is shown as text, not in an image, unless its look is essential, as in a logo

For: 1.4.5

  • Only a person can check it
  • Tools: The browser's developer tools
  1. Look for images that contain words: banners, headings, buttons, quotes, menus.

2.1 Keyboard Accessible

For: 2.1.1

  • Only a person can check it

Signing in doesn't require remembering, transcribing or solving something, unless a way around it is offered

For: 3.3.8

  • Only a person can check it
  • Tools: a browser only
  1. Go through each way the site lets you sign in or verify yourself, with a test account.
  2. Note each step that asks you to remember something (a password), transcribe it (a code from another device), or solve something (a puzzle, a calculation, picking images).
  3. For a password or code, check that you can paste it and that a password manager can fill it, so it needn't be remembered or retyped.

Fails when
