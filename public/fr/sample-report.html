ℹ invalid-field-error-message (À vérifier, gravité grave)
WCAG 3.3.1
Sélecteur : #email
Ce champ est marqué comme invalide, mais le message d’erreur que nomme aria-errormessage est masqué. — Affichez le message d’erreur tant que le champ est invalide.

Échec probable : Le message d’erreur lié au champ est masqué : l’erreur n’est probablement pas signalée.

Comment vérifier
  1. Rendez le champ non valide comme le ferait un utilisateur (soumettez le formulaire vide, ou saisissez une valeur erronée).
  2. Cherchez le message d’erreur vers lequel pointe le champ (son aria-errormessage), et vérifiez s’il apparaît à l’écran.
  3. Sinon, cherchez tout texte qui indique ce qui ne va pas : dans le label, à côté du champ ou dans un récapitulatif en haut du formulaire.
  4. Avec un lecteur d’écran, placez-vous sur le champ et écoutez si l’erreur est annoncée.

Réussite : L’erreur est indiquée par un texte, et annoncée, à un endroit rattaché au champ, même si ce n’est pas dans le message que désigne aria-errormessage.

Échec : Aucun texte n’indique quel champ est erroné ni pourquoi, ou l’utilisateur de lecteur d’écran n’en est pas informé, ce qui ne respecte pas le critère WCAG 3.3.1.

Comprendre 3.3.1 Error Identification

ℹ img-alt-quality (À vérifier, gravité mineure)
WCAG 1.1.1
Sélecteur : html > body > main > img:nth-of-type(2)
L’équivalent textuel de cet <img> ressemble à un nom de fichier. — Un nom de fichier n’apprend rien sur l’image à quelqu’un qui ne la voit pas (échec WCAG F30). Remplacez-le par un texte qui dit ce que montre l’image ou, sur un lien ou un bouton, où il mène ou ce qu’il fait. Ne le gardez que si le nom de fichier est lui-même ce que montre l’image, comme une capture d’écran d’une liste de fichiers.

Échec probable : Un nom de fichier, une adresse web ou un mot générique ne dit pas ce que montre l’image. Attention : Le mot est peut-être tout ce que montre l’image, par exemple une image de ce mot.

Comment vérifier
  1. Repérez l’image indiquée par le rapport et lisez son texte alt (le rapport donne la raison pour laquelle il semblait suspect, le cas échéant).
  2. Regardez l’image et son contexte, et demandez-vous ce qu’elle montre d’important pour la page.
  3. Déterminez si l’alt le dit ; un nom de fichier, une adresse web ou un mot générique comme « image » ne le dit pas.

Réussite : Le texte alt transmet ce que montre l’image et dont l’utilisateur a besoin, avec des mots adaptés au contexte.

Échec : Le texte alt ne transmet pas le contenu de l’image, par exemple un nom de fichier, une adresse ou un mot générique, ce qui ne respecte pas le critère WCAG 1.1.1 (F30).

ℹ duplicate-id (À vérifier, gravité modérée) × 2
WCAG 4.1.1
Sélecteur : html > body > main > form > input:nth-of-type(2)
L’identifiant « code » est utilisé sur 2 éléments du même arbre. — Donnez à chaque élément son propre identifiant. Un doublon casse <label for>, les liens d’ancrage, getElementById et tout attribut de référence par identifiant : tous ne résolvent que la première correspondance.

Réussite probable : Les WCAG 2.2 ont supprimé le critère au regard duquel ce point a été relevé. Attention : Le défaut lui-même casse toujours ce qui en dépend, et une norme qui conserve le critère le considère comme un échec.

Comment vérifier
  1. Inspectez les éléments indiqués par le rapport et notez l’id qu’ils partagent.
  2. Vérifiez si quelque chose fait référence à cet id : l’attribut for d’un label, un attribut aria-* comme aria-labelledby, ou un lien vers #the-id.
  3. Si quelque chose y fait référence, suivez la référence (cliquez sur le label ou le lien, ou lisez le nom dans le panneau Accessibilité) et vérifiez qu’elle atteint l’élément voulu.
  4. Vérifiez quelle version des WCAG et quelle norme l’audit applique ; selon WCAG 2.2, ou 2.0/2.1 avec l’errata de 2023, le critère 4.1.1 est satisfait pour le HTML.

Réussite : Rien ne casse à cause du doublon (les références atteignent l’élément voulu) et l’audit utilise WCAG 2.2, ou 2.0/2.1 avec l’errata, selon lesquels le critère 4.1.1 est satisfait.

Échec : Un label, une référence ARIA ou un lien atteint le mauvais élément (WCAG 1.3.1 ou 4.1.2), ou l’audit suit une norme qui conserve le texte du critère 4.1.1, comme l’EN 301 549 V3.2.1, selon laquelle les id en double ne respectent pas le critère 4.1.1 (F77).

À examiner par une personne

ℹ manual-review (À vérifier, gravité modérée)
WCAG 2.1.1WCAG 2.4.3WCAG 2.4.7
Sélecteur : html
Vérifiez à la main la navigation au clavier et l’ordre du focus. — Parcourez la page avec la touche Tab et vérifiez que chaque élément interactif peut être atteint et utilisé au clavier, et que le focus peut toujours en sortir ; que l’ordre du focus suit l’ordre de lecture, y compris après qu’un script a ouvert ou ajouté du contenu ; et que le focus est toujours visible.
Comment vérifier
  1. Cliquez dans la barre d’adresse du navigateur, puis appuyez plusieurs fois sur Tab pour parcourir chaque lien et chaque contrôle de la page.
  2. À chaque arrêt, vérifiez que vous voyez où se trouve le focus, et que l’ordre suit l’ordre de lecture de la page.
  3. Actionnez chaque contrôle au clavier (Entrée, Espace, touches fléchées), et ouvrez et fermez les menus et les boîtes de dialogue.
  4. Vérifiez que le focus ne reste jamais bloqué dans un composant et que Échap ou Tab permet de continuer.

Réussite : Tout fonctionne au clavier, le focus se déplace dans un ordre logique, reste toujours visible et n’est jamais bloqué.

Échec : Un élément ne peut pas être atteint ou utilisé au clavier, le focus piège l’utilisateur, l’ordre est déroutant ou le focus est invisible, ce qui ne respecte pas les critères WCAG 2.1.1, 2.1.2, 2.4.3 ou 2.4.7.
