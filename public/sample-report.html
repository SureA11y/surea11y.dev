1.1.1 Non-text Content Scan: Fail Checks: 5

Non-text content that conveys something has a text alternative

Rules decide part of it · Tools: The browser's developer tools

  1. Look through the whole page for content that isn't text: photos, icons, logos, charts, maps, diagrams, video posters, and the pictures inside buttons and links.
  2. For each, select it in the developer tools' Elements pane and read the Name in its Accessibility pane.
  3. Note each one that has no name and isn't hidden from assistive technology (with alt="", aria-hidden="true", role="presentation" or as a CSS background).
  4. Look also for information that only CSS shows: background images, icon fonts and pictures added with the content property. Inspect each, since there is no alt attribute to read, and check that what it shows is also given in text that a screen reader reads.
  5. For content that can't be described in a few words, such as a chart or a map, check that the name at least says what it is, and that a fuller description is on the page or linked beside it.

Passes when: Every piece of non-text content a person needs has a text alternative, or is hidden from assistive technology because it is decorative.

Fails when: Non-text content that conveys something has no text alternative, so a screen reader user meets an unnamed image or nothing at all, which fails WCAG 1.1.1.

Images and icons used as controls are named by what they do

Rules decide part of it · Tools: The browser's developer tools

  1. Find every link, button and other control whose only content is an image or icon, such as a logo that links home, a magnifier for search or a cross that closes a dialog.
  2. For each, select it in the developer tools' Elements pane and read the Name in its Accessibility pane.
  3. Check that the name says what the control does or where it leads ("Search", "Close", "Home"), not what the picture shows ("magnifying glass") or a file name.

Passes when: Every control made of an image or icon has a name that says what it does or where it goes.

Fails when: A control made of an image or icon has no name, or one that describes the picture rather than what it does, which fails WCAG 1.1.1.

Decorative images are hidden from assistive technology, and only those

Only a person can check it · Tools: The browser's developer tools

  1. Look through the page for images, icons and graphics that only decorate: borders, dividers, background pictures, ornaments, and pictures whose content the text next to them already gives.
  2. For each, select it in the developer tools' Elements pane and check in its Accessibility pane that it is ignored (alt="", aria-hidden="true", role="presentation", or a CSS background).
  3. For a decorative SVG drawn in the page, check that it has aria-hidden="true". Without it, some browser and screen reader pairs announce it as an image with no name, or read the text inside it.
  4. Then do the reverse: for each image that is hidden that way, ask whether a user would miss anything if it were gone: information, a label, a chart's data.

Passes when: Decorative images are hidden from assistive technology, and every image that is hidden is truly decorative.

Fails when: A decorative image is announced (often by its file name), or an image that conveys information is hidden from assistive technology, which fails WCAG 1.1.1.

Each text alternative gives what its image gives

Rules decide part of it · Tools: The browser's developer tools

  1. For each image and other non-text content that has a text alternative, read the alternative (the Name in the developer tools' Accessibility pane) and look at the content in its place on the page.
  2. Ask what the content gives a reader there, and check that the alternative gives the same: the words in an image of text, the point a photo makes, the facts a chart shows.
  3. Where the alternative only names a complex image, such as a chart or diagram, check that the details are in a caption, text or table next to it, or a link beside it, that a screen reader user can find from the image.
  4. Note alternatives that are a file name, a web address, a word such as "image" or "photo", or that repeat the text right next to them.
  5. Check the language of each alternative: it should be in the language of the page, or marked with its own.

Passes when: Each text alternative gives what its content gives in that place, directly or through a description a screen reader user can reach from it.

Fails when: A text alternative doesn't give what the content does, for example a file name, a generic word or a chart named without its data anywhere, which fails WCAG 1.1.1 (F30).

1.2.2 Captions (Prerecorded) Scan: Needs review Checks: 2

Prerecorded video with sound has captions

Only a person can check it · Tools: a browser only

  1. Find every prerecorded video with sound on the page, including ones in frames and players of other sites.
  2. Play each with the sound on and note whether its sound carries information: speech, or sounds that matter.
  3. Where it does, look for captions: the player's CC button, captions burned into the picture, or a captioned version of the same video linked next to it. A transcript on its own doesn't replace captions.
  4. Leave out a video that is itself an alternative for text on the page and is labelled as such.

Fails when: A prerecorded video has dialogue or important sounds and no captions, here or in a linked captioned version, even if a transcript is offered, which fails WCAG 1.2.2.

Captions give all the dialogue, who is speaking, and the sounds that matter, in time with the video

Only a person can check it · Tools: a browser only

  1. Play each captioned video with the sound on and the captions turned on.
  2. Compare the captions with what is said and heard, all the way through.
  3. Check that they carry all the dialogue, say who is speaking when that isn't clear, and describe the sounds that matter (music, alarms, laughter), and that they stay in time with the picture.

Passes when: The captions carry all dialogue, the speakers where needed, and the important sounds, in time with the video.

Fails when: Captions leave out dialogue or important sounds, don't say who is speaking where that matters, or run out of time with the video, which fails WCAG 1.2.2 (F8).

1.3.1 Info and Relationships Scan: Needs review Checks: 6

Text that looks like a heading is marked up as one, at a level that matches the page's outline

Rules decide part of it · Tools: The browser's developer tools, A screen reader

  1. Look through the page and note every piece of text that works as a heading: it is larger or bolder than the text around it and introduces what follows.
  2. For each, check in the developer tools' Elements pane that it is an <h1> to <h6>, or has role="heading" with an aria-level.
  3. Check the reverse: each heading element on the page introduces content, rather than being used only to make text big.
  4. List the headings with a screen reader's headings list, a browser extension such as HeadingsMap, or the Accessibility pane, and check that their levels match the structure the page shows: a section's sub-headings sit below its heading, not at the same level or above it. A skipped level on its own, such as an h2 followed by an h4, doesn't fail this criterion when the nesting is still right. Record it as a best practice issue.

Passes when: Every visual heading is marked up as a heading, every heading element is one, and the levels follow the outline the page shows.

Fails when: Text that looks like a heading is plain text, a heading element is used only for its size, or the levels contradict the outline, so screen reader users can't find or follow the sections, which fails WCAG 1.3.1.

Rules decide part of it · Tools: The browser's developer tools

  1. Look through the page for content shown as a list: items in a row or column with bullets, numbers or the same layout, such as menus, steps and groups of links.
  2. For each, check in the developer tools' Elements pane that it is a <ul>, <ol> or <dl> (or has role="list" with role="listitem" items).
  3. Check that each list holds only list items directly, and each list item sits in a list.

Passes when: Content shown as a list is marked up as a list, and list markup is complete.

Fails when: Content shown as a list is a run of paragraphs, line breaks or divs, or list markup is broken, so a screen reader doesn't say it is a list or how many items it has, which fails WCAG 1.3.1.

Data tables mark up their headers and caption, and tables used only for layout carry no header markup

  2. For a table of data, check in the developer tools' Elements pane that its header cells are <th> (with scope where a header is not plainly a row or column header) and that a title shown above it is its <caption>.
  3. For a complex table, with headers on more than one level, check that each data cell names its headers with a headers attribute or scope.
  4. With a screen reader, move through a few data cells and check that it reads their headers with them.
  5. For a table used only to lay things out, check that it has no <th>, <caption> or summary.

Fails when: A table of data has no header markup or a fake caption in a cell, data is laid out as a grid without a table, or a layout table is marked up as data, which fails WCAG 1.3.1.

  1. Find every form field on the page: text fields, check boxes, radio buttons, drop-downs and custom controls.
  2. For each, select it in the developer tools' Elements pane and check that the Name in its Accessibility pane contains its visible label.
  3. For a group of fields under one question, such as radio buttons or a date in three parts, check that the group is a <fieldset> with a <legend>, or has role="group" with a name, so the question is read with each field.
  4. Check that instructions shown next to a field (a format, a required mark) are tied to it with aria-describedby or are in its label.

Passes when: Every field's name includes its visible label, groups of fields are named by their question, and a field's instructions are tied to it.

Fails when: A field is labelled only by nearby text that isn't tied to it, or a group's question isn't tied to its fields, so a screen reader reads a field without saying what it is for, which fails WCAG 1.3.1.

ARIA roles and relationships give the same structure the page shows

Rules decide part of it · Tools: The browser's developer tools

  1. Find the parts of the page built with ARIA roles: custom menus, tabs, trees, grids, lists and listboxes.
  2. For each, open the developer tools' Accessibility tree and check that the structure it shows matches what is on screen: a tablist holding tabs, a menu holding menu items, a grid holding rows and cells.
  3. Check that no element with a role is missing the parent or children its role needs, and that aria-owns, where used, gives each element a single owner.
  4. Check that <body> is not hidden with aria-hidden="true".

Passes when: The accessibility tree gives the structure the page shows, with every role in the place its role needs.

Fails when: A role is missing its required parent or children, owned twice, or the page is hidden from the tree, so assistive technology gives a structure that doesn't match the screen, which fails WCAG 1.3.1.

Meaning shown by styling or layout, such as bold, colour, position or an asterisk, is also given in the markup or the text

Only a person can check it · Tools: The browser's developer tools, A screen reader

  1. Look for meaning that the page shows only by how things look: required fields marked by an asterisk or colour, emphasised or struck-through words, a selected item shown by its style, text set apart in a box.
  2. For each, check whether the same meaning is in the markup (such as required, aria-current, <em>, <del>) or in the text itself ("required", "current page").
  3. Look at text and icons added with CSS, through the content property. Browsers differ in whether screen readers read them, so information that only CSS adds must also be in the markup or the text.
  4. Read the parts with a screen reader and check that what the styling shows is said.

Passes when: Whatever the styling or layout conveys is also in the markup or the text.

Fails when: Meaning is given only by styling or position, such as required fields marked only by colour or an unexplained asterisk, so a screen reader user misses it, which fails WCAG 1.3.1.

1.3.5 Identify Input Purpose Scan: Needs review Checks: 1

1.4.3 Contrast (Minimum) Scan: Fail Checks: 1

Rules decide part of it · Tools: The browser's developer tools

  1. Look through the page for text that seems faint against its background: light grey text, text on coloured panels, placeholders, text over images or gradients, text in buttons.
  2. For each, inspect it and click the swatch of its colour in the developer tools' Styles pane: the picker shows its contrast ratio with the background.
  3. The colour picker measures against the background colour set in CSS. Where text sits on an image, a gradient or a semi-transparent layer, or its colour comes from opacity or a blend mode, the picker's figure is not reliable: use the next step instead.

Passes when: All text and images of text have a contrast of at least 4.5:1 with their background, or 3:1 when large.

Fails when: Text has less contrast with its background than 4.5:1 (3:1 for large text), so people with low vision can't read it, which fails WCAG 1.4.3.

Passes when: At 200% all text has grown and stays readable, and everything still works.

Fails when: At 200% text is cut off, overlaps or doesn't grow, a control stops working, or pinch zoom is blocked, which fails WCAG 1.4.4.

1.4.12 Text Spacing Scan: Needs review Checks: 4

With the 1.4.12 spacing applied, no text is cut off or made to overlap (measured in a browser)

Only a person can check it · Tools: A keyboard

  5. This criterion only asks that headings and labels which exist describe their content. A missing heading or label is checked under 1.3.1 or 3.3.2, not here.

Passes when: Every heading says what the content under it is about.

Fails when: A heading doesn't describe the content under it, such as "Section 1" or a file name, which fails WCAG 2.4.6.

Labels describe their fields, and fields with the same label can be told apart

Only a person can check it · Tools: a browser only

  1. Read the visible label of every field and control on the page.
  2. Check that each says what to enter or choose, such as "Email address" rather than "Field 1" or "Text".
  3. Where several fields share a label, such as "Name" twice, check that the page makes clear which is which, by a group heading or the rest of the label.

Passes when: Every label says what its field or control is for, and fields with the same label are told apart.

Fails when: A label doesn't say what its field is for, or several fields have the same label with nothing telling them apart, which fails WCAG 2.4.6.

2.4.7 Focus Visible Scan: Needs review Checks: 1

Every element that takes keyboard focus shows that it has it

Rules decide part of it · Tools: A keyboard

  1. Reload the page and press Tab slowly through the whole page.
  2. At each stop, check that you can see which element has focus: an outline, a change of colour, an underline or another visible change.
  3. Use the keyboard, not the mouse, to move focus. Browsers show the focus of an element clicked with the mouse differently from one reached with Tab, so a mouse test proves nothing here.
  4. Note each stop where you can't tell where focus is, and each time focus seems to disappear for a press or more.
  5. Do the same inside menus, dialogs and widgets that use the arrow keys.
  6. Turn on a contrast theme in Windows and repeat a few stops. A focus style drawn only with box-shadow or a background colour disappears in that mode. WCAG doesn't require it to show there, but record it as a best practice issue.

Passes when: At every stop you can see which element has focus.

Fails when: Focus reaches an element with no visible change, or lands on something hidden or off screen, so keyboard users lose track of where they are, which fails WCAG 2.4.7.

2.4.9 Link Purpose (Link Only) Scan: Needs review Checks: 1

Each link's purpose can be told from its text alone

Rules decide part of it · Tools: The browser's developer tools, A screen reader

  1. List the page's links with a screen reader's links list, which shows them without their context.
  2. Check that each link's name alone says where it goes or what it does.
  3. Check that links with the same name lead to the same place, and links to different places have different names.
  4. Leave out a link whose purpose would be ambiguous to everyone.

Passes when: Every link's name alone says where it goes, and same names mean same destinations.

Fails when: A link's purpose can only be told from its context, or two links with the same name lead to different places, which fails WCAG 2.4.9.

2.5.3 Label in Name Scan: Not applicable Checks: 1

A control's name contains the text of its visible label

Rules decide part of it · Tools: The browser's developer tools

  1. Find every control with a visible label made of text: buttons, links, fields, tabs, menu items, and controls labelled by text next to them.
  2. For each, read its Name in the developer tools' Accessibility pane.
  3. Check that the name contains the visible label's words, in the same order, ideally at the start (a button showing "Send" named "Send message", not "Submit").
  4. Ignore differences of case and punctuation when you compare. Text shown as an image counts as a visible label too.
  5. Leave out a label made only of symbols, such as "×" or ">": the name should say what it does.
  6. Leave out controls with no visible text, such as an icon-only button: they have no visible label to match.

Passes when: Every control's name contains the words of its visible label, in order.

Fails when: A control's name doesn't contain its visible label, so someone who uses speech input can't activate it by saying what they see, which fails WCAG 2.5.3.

2.5.8 Target Size (Minimum) Scan: Needs review Checks: 1

Targets are at least 24 by 24 CSS pixels, or far enough apart

Rules decide part of it · Tools: The browser's developer tools

  1. Look for small controls: icons, close buttons, pagination, links in a row, small check boxes.
  2. Inspect each and read the size of the area that responds to the pointer, which can be larger than the visible icon, in the developer tools' box model. Check that it is at least 24 by 24 CSS pixels.
  3. Where it is smaller, check whether a 24-pixel circle centred on it would touch another target, or the circle of another small target.
  4. Leave out links in a sentence or paragraph, controls the browser draws unstyled, controls with a full-size equivalent elsewhere on the page, and targets whose size is essential, such as a map's pins.

Passes when: Every target is at least 24 by 24 CSS pixels, or far enough from others, or one of the exceptions.

Fails when: A target smaller than 24 by 24 CSS pixels sits so close to another that their 24-pixel circles overlap, with no exception that applies, which fails WCAG 2.5.8.

3.1.1 Language of Page Scan: Needs review Checks: 1

The page's main language is given in its markup, and is the right one

Rules decide part of it · Tools: The browser's developer tools

  1. Read the lang attribute of the <html> element in the developer tools' Elements pane.
  2. Check that it is a language code (en, fr, pt-BR) and that it is the language most of the page's text is in.
  3. Where <html> also has xml:lang, check that both give the same language.
  4. In a single-page application, change the interface language and check that lang changes with it. A screen reader switches voice only if one for that language is installed, so judge by the markup, not only by what you hear.

Passes when: The <html> element's lang gives the language most of the page is in.

Fails when: The page has no lang, a wrong or invalid one, so screen readers read it with the wrong voice and pronunciation, which fails WCAG 3.1.1.

3.1.2 Language of Parts Scan: Needs review Checks: 1

Passages and phrases in a language other than the page's are marked with their own language

Rules decide part of it · Tools: The browser's developer tools, A screen reader

  1. Read through the page and note passages, quotes, phrases and names of things written in another language than the page's, including a language picker's options.
  2. For each, check in the developer tools' Elements pane that it, or an element around it, has a lang attribute with that language's code.
  3. Leave out proper names, technical terms, and words that have become part of the page's language, such as "café" in English.
  4. Listen to a few with a screen reader to check it switches pronunciation.

Passes when: Every passage or phrase in another language is marked with a valid lang attribute for that language.

Fails when: A passage or phrase in another language isn't marked with its language, or is marked with a wrong code, so it is read with the wrong pronunciation, which fails WCAG 3.1.2.

3.2.5 Change on Request Scan: Needs review Checks: 1

Changes of context happen only when the user asks for them, or can be turned off

Rules decide part of it · Tools: A keyboard

  1. Use the page and note every change of context: a new page or window, a form sent, focus moved, content replaced.
  2. For each, check that it happened because you asked for it, such as pressing a button or link, and not by itself, on a timer, or as a side effect.
  3. Check that links that open a new window say so, and that the page doesn't refresh or redirect by itself, or offers a way to turn that off.

Passes when: Every change of context happens on the user's request, or can be turned off.

Fails when: The context changes by itself, such as a page that refreshes, redirects or opens a window without being asked, which fails WCAG 3.2.5.

3.3.1 Error Identification Scan: Needs review Checks: 1

An input error the page detects is shown in text that says which field is wrong and what is wrong

Rules decide part of it · Tools: A keyboard, A screen reader

  1. Find each form on the page and send it empty, then with wrong values: a malformed email, letters in a number field, a date in the past.
  2. Check that each error the page detects is shown in text, not only by colour or an icon, next to the field or in a list at the top.
  3. Check that the text says which field is wrong and what is wrong with it.
  4. The browser's own validation messages count as text, but their wording and how long they stay on screen differ between browsers. Check them in each browser you test.
  5. Check with a screen reader that the error is announced or reached easily, and that each wrong field is marked invalid.

Passes when: Every input error the page detects is shown in text that names the field and the problem.

Fails when: An input error is shown only by colour or an icon, not at all, or without saying which field is wrong, which fails WCAG 3.3.1.

3.3.2 Labels or Instructions Scan: Needs review Checks: 1

Fields that ask for input have a visible label, and instructions where the input needs them

Rules decide part of it · Tools: The browser's developer tools

  1. Find every field and control that asks for input on the page.
  2. Check that each has a label you can see without hovering or typing: not only a placeholder that disappears when you type, or a title shown on hover.
  3. Where the input must follow rules, such as a date format, a password's requirements or which fields are required, check that the page says so before the user sends it.
  4. This criterion asks only that labels and instructions are shown. Whether a label is tied to its field in the markup is checked under 1.3.1 and 4.1.2.

Passes when: Every field has a visible label, and the page gives the instructions the input needs before it is sent.

Fails when: A field has no visible label, only a placeholder or a hover title, or input rules are given only after an error, which fails WCAG 3.3.2.

3.3.8 Accessible Authentication (Minimum) Scan: Needs review Checks: 1

Signing in doesn't require remembering, transcribing or solving something, unless a way around it is offered

Only a person can check it · Tools: a browser only

  1. Go through each way the site lets you sign in or verify yourself, with a test account.
  2. Note each step that asks you to remember something (a password), transcribe it (a code from another device), or solve something (a puzzle, a calculation, picking images).
  3. For a password or code, check that you can paste it and that a password manager can fill it, so it needn't be remembered or retyped.
  4. Check that a password manager actually fills the fields: the username and password fields need autocomplete="username" and autocomplete="current-password" (or new-password), and a one-time code field works best with autocomplete="one-time-code".
  5. Where a code is split into one box per digit, paste the whole code into the first box and check that it fills them all. Boxes that block pasting, or take only one character each, fail.
  6. For other tests, check that another method is offered, or that the test only asks to recognise objects or something you gave the site.
  7. Count a CAPTCHA shown during sign-in as part of the sign-in. Other methods that need no cognitive test, such as a passkey, a sign-in link sent by email or signing in through a third party, are valid alternatives.

Passes when: Every sign-in step that asks to remember, transcribe or solve something allows pasting and password managers, or offers another way, or only asks to recognise objects or your own content.

Fails when: Signing in requires remembering, transcribing or solving something with no way around it, such as a code field that blocks pasting, which fails WCAG 3.3.8.

4.1.2 Name, Role, Value Scan: Needs review Checks: 4

Every link, control, frame and dialog has a name that says what it is for

Rules decide part of it · Tools: The browser's developer tools, A screen reader

  1. Go through every link, button, field, frame and custom control on the page, by pressing Tab and inside widgets with the arrow keys.
  2. For each, read the Name in the developer tools' Accessibility pane, or listen to what a screen reader says.
  3. Check names in two browser and screen reader pairs. Names built from aria-labelledby, from a label that wraps the control, or from CSS content can differ between them.
  4. Check that each has a name that says what it is for, including icon-only buttons, frames ("Video player", "Map") and dialogs.
  5. Check that frames with the same name show the same thing, and that names given only for braille have a spoken equivalent.

Passes when: Every link, control, frame and dialog has a name that says what it is for.

Fails when: A link, control, frame or dialog has no name, or one that doesn't say what it is for, so assistive technology announces only its role, which fails WCAG 4.1.2.

Every control's role says what it does, and controls aren't nested inside one another

Rules decide part of it · Tools: The browser's developer tools, A screen reader

  1. For each control on the page, note what it does when used: opens a page (a link), acts on the page (a button), toggles (a check box or switch), opens a list (a menu or combo box).
  2. Read its Role in the developer tools' Accessibility pane, or listen to a screen reader, and check that the role matches what it does.
  3. Pay attention to custom controls built from divs and spans, links used as buttons and buttons used as links.
  4. Check that no control holds another one inside it, such as a button inside a link, and that controls whose children are presentational, such as a tab or a button, hold nothing focusable.

Passes when: Every control's role says what it does, and no control is nested inside another.

Fails when: A control has no role, a wrong one (a clickable div with no role, a link that acts as a button), or holds another control inside it, which fails WCAG 4.1.2.

Every control's state and value are exposed and change with what is on screen

Rules decide part of it · Tools: The browser's developer tools, A screen reader, A keyboard

  1. Find the controls that have a state or value: check boxes, switches, radio buttons, expandable sections and menus, tabs, sliders, selected items, pressed buttons.
  2. Read each one's state and value in the developer tools' Accessibility pane, or listen with a screen reader: checked, expanded, selected, pressed, the current item (aria-current), and the current value of a slider or spin button.
  3. Change each with the keyboard and check that the state or value read changes with what you see.
  4. For an expandable control, check that it says expanded only while what it opens is shown.

Passes when: Every control's state and value are exposed and change with what is on screen.

Fails when: A control's state or value isn't exposed, or doesn't change when it changes on screen, such as a custom check box always read as not checked, which fails WCAG 4.1.2.

ARIA attributes are real, valid and allowed where they are, and nothing focusable is hidden from assistive technology

Rules decide part of it · Tools: The browser's developer tools

  1. In the developer tools' Elements pane, search the markup for aria- and role= and look at each use.
  2. Check that each aria-* attribute is a real one, has a valid value, and is allowed on its element's role.
  3. Check that ids that aria-labelledby, aria-describedby, aria-controls and the like point to exist once each.
  4. Check that nothing that takes focus is inside an element with aria-hidden="true", and that <body> isn't hidden.

Passes when: ARIA attributes are real, valid and allowed where they are, their ids are unique, and nothing focusable is hidden.

Fails when: An ARIA attribute is misspelt, has an invalid value or is not allowed on its role, an id it points to is missing or repeated, or something focusable is hidden from assistive technology, which fails WCAG 4.1.2.

4.1.3 Status Messages Scan: Needs review Checks: 1

Status messages are announced by assistive technology without taking focus

Only a person can check it · Tools: A screen reader

  1. Find the messages the page shows without moving focus: "Added to cart", search result counts, "Saved", progress, form errors listed after sending.
  2. Turn on a screen reader and cause each message, by the action that shows it.
  3. Check that the screen reader says the message without focus moving to it.
  4. Repeat in a second browser and screen reader pair. Live regions are among the least consistent parts of screen reader support.
  5. Where it says nothing, check in the developer tools that the message is in an element with role="status", role="alert" or aria-live, and that the element is not hidden. A role="status" or aria-live region must already be on the page, empty, before the message is put in it. An element with role="alert" is usually announced even when it is added together with its message.
  6. Leave out messages that receive focus, or that come with a new page: those are not status messages, and are checked under other criteria.

Passes when: Every status message is announced by a screen reader without focus moving to it.

Fails when: A status message appears on screen but a screen reader doesn't say it, which fails WCAG 4.1.3.

To record a result and notes for each check, make a worksheet of them: core's renderProcedures, or the CLI's scan --manual-checks.
